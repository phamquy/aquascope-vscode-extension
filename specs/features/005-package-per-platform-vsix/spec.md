# Package per-platform VSIX with toolchain

## Why

The extension works today only for someone who has built spike 002's toolchain and pointed `aquascope.toolchainPath` at it. ADR 0002 decided that users install nothing but the extension: each platform gets its own VSIX that carries a prebuilt `cargo-aquascope` and a trimmed copy of the pinned nightly toolchain. Feature 003 already looks for that copy inside the extension when the setting is empty (003 R3). This feature produces those packages, so that installing one VSIX is enough to see the diagrams.

Spike 002 settled how the bundle is made, and features 003 and 004 narrowed what it must do. A `cargo-aquascope` built from the pinned Aquascope tag runs against only the `rustc`, `cargo` and `rust-std` components. With the tools `cargo check` never uses removed, the binaries and toolchain measured 370 MB unpacked and 120 MB zipped at the compression `vsce` uses, on darwin-arm64. The spike's two exceptions to "install nothing", a system linker and the network for dependencies, do not arise in this version: feature 003 analyses one file at a time in a crate with no dependencies, offline, and `cargo check` of such a crate links nothing. The evidence is in Appendix A.

Redistributing the toolchain and the Aquascope binaries brings licence obligations that the spike did not meet. Its trimming deleted the toolchain's `share/` folder, which holds the Rust licence files. The binaries statically link the crates Aquascope depends on, whose licences ask for their notices to travel with them. And feature 004 left a notice for the libraries inside the vendored frontend to packaging. This feature ships all of them (D4), and gives the extension its own `LICENSE` file (D5).

Two details of the build shape the requirements. `vsce` packages the folder it runs in, so the bundle must sit at `aquascope/` in the repository root while it packages. A bundle left there would quietly change F5 and the tests, so the script builds and tests the bundle elsewhere and places it at the root only for that step. The test suite also skips its end-to-end tests when it finds no bundle, so the script must treat a skipped toolchain test as a failure, or a misplaced bundle would pass untested.

## Decisions

D1 to D3 were recorded on 2026-11-06 from the draft's open questions, D4 and D5 from its review; the spec was approved the same day.

- D1 (was Q1): The first version packages darwin-arm64 only. linux-x64 comes next; Windows needs a dedicated check first, because feature 003's Windows code paths (`taskkill`, `.exe` names, `PATH` as the library path) have never run.
- D2 (was Q2): Packages are built by a local script on a machine of the target platform, the maintainer's Mac for darwin-arm64. It takes everything from the pin and the repository, so that a CI job on the same platform can run it unchanged; later platforms extend its platform check and trim list.
- D3 (was Q3): Packages reach users as VSIX files, installed with "Extensions: Install from VSIX…". Publishing to the Marketplace, with its undocumented size limit, is a later feature.
- D4: The package ships the licence notices of the crates statically linked into the Aquascope binaries, generated by the script from the pinned `Cargo.lock`.
- D5: The extension gets its own `LICENSE` file, MIT, "Copyright (c) 2026 Jack Pham", matching `package.json`. Without one, `vsce` stops at an interactive prompt, which would block the script.

### User stories

- As a Rust learner, I want to install the extension and analyse a function straight away, so that I do not have to build or configure a toolchain.
- As the maintainer, I want one command to build, test and package the extension for a platform from the pinned versions, so that a release is repeatable and every package is tested with exactly the toolchain it ships.

## Requirements

- R1: `npm run package` runs a packaging script that builds the VSIX for the platform it runs on. In this version that is darwin-arm64: the rustup host `aarch64-apple-darwin`, `vsce` target `darwin-arm64`. On any other platform it stops with a message (D1). It needs rustup, git, the Xcode Command Line Tools, Node and npm, and the network while building.
- R2: The script takes the Aquascope repository, tag and commit and the nightly from `spikes/002-toolchain-bundling/pin.env`, the pin all scripts share. It stops before building if the Aquascope checkout is at a different commit, or if the checkout's `rust-toolchain.toml` names a different nightly.
- R3: The script installs the pinned nightly with rustup and the components needed to build (`rust-src`, `rustc-dev`, `llvm-tools-preview`, `miri`). It then builds `cargo-aquascope` and `aquascope-driver` at the pinned tag, as spike 002 did.
- R4: The script copies the minimal toolchain from that installation, using rustup's manifests for the `rustc`, `cargo` and `rust-std` components, so that the bundled compiler library is the one the binaries were built against. It removes what spike 002 removed (`measure-bundle.sh`), except the licence files under `share/doc/rust/` (`COPYRIGHT.html`, `COPYRIGHT-library.html`, `licenses/`) and `share/doc/cargo/` (`LICENSE-*`). The binaries are copied unmodified.
- R5: The script assembles the bundle in a staging folder that is ignored by git and by `.vscodeignore`, in the layout of 003 R3 (`bin/`, `toolchain/`).
  - **Tests:** it runs the typecheck, the linter and the full test suite with `AQUASCOPE_TEST_TOOLCHAIN` pointing at the staging bundle. A failure, or any toolchain test that skips, stops the script.
  - **Packaging:** only then does it copy the bundle, as real files, to `aquascope/` at the repository root, which is ignored by git but not by `.vscodeignore`, and run `vsce package --target darwin-arm64`.
  - **Clean-up:** it deletes the previous VSIX for the target before starting, and removes `aquascope/` from the root afterwards, also when it fails.
- R6: The package carries only what a run needs: the two Aquascope binaries, the trimmed toolchain and the licence files of R7. It carries no `rustc-dev`, Miri, `rust-src`, rustup, linkers or documentation.
- R7: The package carries the licence notices for everything it redistributes:
  - the extension's own `LICENSE` (D5);
  - the Rust toolchain's licence files kept by R4;
  - Aquascope's MIT licence for the binaries, under `aquascope/`;
  - a notices file under `aquascope/` for the crates in the binaries' dependency graph (D4). The script generates it from the pinned `Cargo.lock` with `cargo metadata`, using each crate's licence texts from the cargo cache, or its licence identifier when the crate ships none;
  - a committed `media/aquascope-embed/THIRD-PARTY-NOTICES`, listing each library bundled in `embed.iife.js` with its version (from the pinned frontend's `pnpm-lock.yaml`), its copyright line and its licence.
- R8: Installed, the package analyses a function with no setting and nothing else installed. With `aquascope.toolchainPath` empty and no Rust toolchain on `PATH`, the command finds the bundled tools (003 R3) and the panel draws the diagram. The binaries remain executable after installing. Nothing is downloaded at install or run time (constitution 6).
- R9: The script prints the path and size of the VSIX it wrote. The README explains how to build a package and how to install it from the VSIX file (D3).
- R10: The package holds no path from the build machine's home folder, where rustup and cargo keep the sources that rustc records in what it builds. The script builds the Aquascope binaries with the home folder remapped to `~` and without rustup's proxy, whose `RUSTUP_HOME` would otherwise be compiled into `aquascope-driver`. It builds the standard library for Miri from copies of its sources in a temporary folder outside the home folder, because `cargo miri setup` takes no compiler flags. (Added after release 0.0.3, which held the path.)

## Acceptance criteria

- [x] AC1: The VSIX's manifest has `TargetPlatform="darwin-arm64"`. It contains the following files, all executable:
  - `extension/aquascope/bin/cargo-aquascope` and `extension/aquascope/bin/aquascope-driver`;
  - `extension/aquascope/toolchain/bin/cargo` and `extension/aquascope/toolchain/bin/rustc`;
  - `extension/aquascope/toolchain/lib/librustc_driver-*.dylib`.

  Every other file under `extension/aquascope/toolchain/` is either listed in the pinned nightly's `rustc`, `cargo` or `rust-std` manifest and not removed by R4, or is one of AC3's licence files.
- [x] AC2: The darwin-arm64 VSIX is at most 150 MB.
- [x] AC3: The VSIX contains:
  - the extension's `LICENSE`;
  - `share/doc/rust/COPYRIGHT.html`, `COPYRIGHT-library.html` and `licenses/`, and `share/doc/cargo/LICENSE-*`, under `extension/aquascope/toolchain/`;
  - Aquascope's licence;
  - a notices file naming every crate in the binaries' dependency graph;
  - `media/aquascope-embed/THIRD-PARTY-NOTICES`.
- [x] AC4: The script's failure handling:
  - **A failing test:** it stops, and no VSIX for the target exists afterwards.
  - **Toolchain tests skipped**, for example because no bundle is found at the staging path: it stops in the same way.
  - **Clean-up:** after a successful run and after a failed one, there is no `aquascope/` folder at the repository root.
- [x] AC5: Checked by hand: on a Mac, or a macOS user account, without rustup and with the network off:
  1. Download the darwin-arm64 VSIX through a web browser.
  2. Install it with "Install from VSIX…" into a fresh profile, with `aquascope.toolchainPath` empty.
  3. Analyse `main` of `05_method_mut_borrow`.

  The panel draws the diagram, and no macOS security dialog appears. If macOS blocks the binaries, the feature goes back to the spec, since signing is out of scope.
- [x] AC6: The script stops before building, naming the mismatch, when the pin names an Aquascope commit other than the checkout's, or a nightly other than the checkout's `rust-toolchain.toml`. Its stop on other platforms is checked by reading the script.
- [x] AC7: The script's output names the VSIX and its size, and the README explains building a package and installing it from the VSIX file.
- [x] AC8: The package check finds no file in the VSIX that holds the build machine's home path, and the packaged binaries and Miri library still analyse and run the fixtures as before (R10).

## Out of scope

- Downloading the toolchain on first run instead of bundling it (ADR 0002's fallback, only if a size limit forces it).
- Code signing and notarisation of the bundled binaries.
- Analysing crates with dependencies, and the linker and network needs that would bring.
- Updating the toolchain separately from the extension; every Aquascope or nightly upgrade is a new package.
- A universal package without a toolchain; `npm run package` builds the platform package (R1).
- Platforms other than darwin-arm64 (D1), building in CI (D2), and publishing to the Marketplace or Open VSX (D3).
- Where the VSIX files are hosted; attaching them to a GitHub release is an optional manual step.
- Checking the vendored embed against the pin; T-023 checked it when it was vendored.

## Open questions

None; the draft's Q1 to Q3 are settled as D1 to D3, and its review's choices as D4 and D5.
